# 卡卡轻量灵动陪伴层 V1 设计

## 背景

当前卡卡已经具备以下能力：

- 12 状态桌宠资源和基于 `pet-status` 的状态分发链路。
- 本地 DeepSeek 聊天、聊天历史、长期记忆、关系记忆和隐私面板。
- `moodEngine` 可根据聊天情绪、最近温度、夜间时段和 Cline 工作状态推导基础 mood。
- `presenceService` 会在长时间连续工作时给出一次关怀提醒，但整体主动反应仍然偏少。
- `headPatService` 已能记录摸头互动，并把它保存为短期 `recentWarmth` 信号。

目前卡卡已经能“回应”，但还不够“灵动”。它缺少一层轻量、低打扰、容易测试的主动节奏规则，去把聊天、摸头、空闲和昼夜这些已有信号串起来，让卡卡更像一只会陪伴、会期待互动的小宠物，而不是只在被动触发时才切换状态。

## 目标

1. 在不新增复杂系统的前提下，让卡卡明显更有“活着”的感觉。
2. 让聊天后、摸头后、空闲时、夜间时的状态和气泡表现更有层次。
3. 保持低打扰，避免影响用户工作流，尤其是 `loading` / `thinking` 期间。
4. 优先复用现有 12 状态资源和现有状态链路，不扩大资源包协议范围。
5. 将规则设计成纯逻辑、可单测的模块，为后续更完整的 mood / companion 系统打基础。

## 非目标

- 第一阶段不引入新的标准宠物状态枚举。
- 不重做完整 mood 状态机，不引入复杂优先级图和大规模持久化结构。
- 不新增数据库、远程存储或复杂用户画像系统。
- 不把卡卡做成高频弹窗式助手，不在工作中频繁打断用户。
- 不要求新增 PNG 素材或动画协议变更。

## 方案选择

本轮考虑过三类方向：

1. `轻量灵动层`
   在现有 mood / presence 之上新增一层很薄的主动规则，只处理短期灵动窗口、轻气泡和低频主动表达。
2. `完整心情机`
   扩展现有 mood 系统为更复杂的状态机，加入衰减、优先级、冷却和完整转换图。
3. `事件驱动陪伴`
   不强调 mood 本体，而是为聊天、摸头、长时间空闲、长时间工作等事件分别挂触发器。

本设计采用 `轻量灵动层`。原因是它最适合第一阶段：

- 改动面小，容易接入现有主流程。
- 可以立刻提升陪伴感，收益明显。
- 规则可以保持集中，避免直接把逻辑打散在多个模块里。
- 后续仍可平滑演进到更完整的 mood 状态机。

## 用户可见行为

第一阶段只在现有 `happy / head-pat / sleepy / message / idle` 等状态基础上增强触发规则，不新增新姿态资源。

### 1. 聊天后的开心窗口

- 聊天成功后，卡卡进入一段短期“开心窗口”。
- 在这段时间里，如果没有更高优先级的工作态或夜间收敛条件，卡卡更容易保持 `happy`。
- 在合适时机，它可以冒一句很轻的互动型气泡，例如表达开心、想继续陪你、期待下一次互动。

### 2. 摸头后的黏人窗口

- 摸头成功后，卡卡进入一段短期“黏人窗口”。
- 这个窗口不改变长期关系等级，也不做游戏化奖励。
- 在窗口期里，卡卡更容易表现为 `happy` 或更温和的亲近感，并允许低频出现轻微求互动气泡。

### 3. 空闲时的小动作感

- 如果用户有一段时间没理卡卡，也不处于长时间工作中，卡卡可以低频地冒一个轻气泡。
- 这种表达不是催促，而是弱存在感，例如“我在喔”“你忙完了可以理理我”。
- 必须受冷却控制，避免短时间连续冒泡。

### 4. 夜间自动收敛

- 夜间依然保留陪伴感，但整体活跃度要明显降低。
- 夜间更偏向 `sleepy`、安静、困困的表达，不做频繁互动提示。
- 夜间可以允许极低频、偏轻柔的气泡，但不能显得很吵。

### 5. 不打断工作

- 当用户当前是 `loading` 或 `thinking` 时，卡卡默认安静。
- 只有当工作时间已经很长，才允许触发一次关怀型提醒，例如喝水、休息一会。
- 工作期间不触发撒娇型、求互动型轻气泡。

## 实现边界

### 不新增复杂持久化层

- 继续复用现有 `relationship.json`、`presenceRuntime` 和主进程状态分发链路。
- 第一阶段不新增单独的数据文件。

### 只新增一个轻量规则模块

- 新增单独的 `playful presence` 规则模块。
- 它负责将已有信号整合成“当前是否应该更灵动”的判断，而不是把逻辑散落到多个现有模块中。

### 不修改标准状态协议

- 不增加 `PetStatus` 枚举值。
- 优先用现有 `happy`、`message`、`sleepy`、`idle` 等状态表达第一阶段行为。

### 允许增加极少关系字段

- 如果现有 `recentWarmth` 不足以表达聊天后和摸头后的短期灵动窗口，可以为 `RelationshipMemory` 增加少量可选时间字段。
- 这些字段只服务于短期节奏规则，不进入 UI，也不扩展成长期成长系统。

### 优先规则可测性

- 第一阶段所有关键行为都应能以纯逻辑方式测试。
- 先把时间窗口、夜间收敛、冷却、工作静默这些基础规则做扎实，再考虑更复杂的 AI 化行为。

## 模块设计

### Relationship 层

继续复用 `RelationshipMemory` 作为短期陪伴信号容器。

建议允许增加极少量可选字段，例如：

```ts
type RelationshipMemory = {
  playfulChatUntil?: string;
  playfulAttachedUntil?: string;
  // existing fields remain
};
```

设计原则：

- `playfulChatUntil` 表示最近聊天带来的短期开心窗口。
- `playfulAttachedUntil` 表示最近摸头带来的短期黏人窗口。
- 这些字段只描述窗口有效期，不直接承载复杂状态机。
- 如果实现时发现 `recentWarmth` 足够复用，也可以减少字段数量，但目标保持不变：短期灵动窗口必须可推导、可测试。

### Playful Presence 模块

新增纯规则模块，例如 `playfulPresence.ts`，输入包括：

- `now`
- `relationship`
- `latestVisibleStatus`
- `userIsReading`
- `longWorkSession`

输出应是一个清晰的纯数据结果，例如：

```ts
type PlayfulPresenceDecision = {
  suggestedStatus?: "happy" | "idle" | "sleepy" | "message";
  bubbleMessage?: string;
  shouldPulse: boolean;
  cooldownUntil?: string;
};
```

这里的关键不是具体类型名，而是职责边界：

- 决定当前是不是处于更灵动的短期窗口。
- 决定是否应该发出轻量气泡。
- 决定夜间是否应收敛。
- 决定当前是否应该静默以避免打扰工作。

该模块不直接操作文件、不直接发 IPC、不直接推送 UI，只返回可消费的规则结果。

### Main 进程接入点

#### 聊天成功后

- 在聊天成功链路里更新短期开心窗口。
- 然后继续使用现有 `createChatMoodStatus` / `notifyRenderer` 链路推送即时状态。

#### 摸头成功后

- 在 `recordHeadPatInteraction` 成功后，更新短期黏人窗口。
- 继续保留现有即时 `head-pat` / `happy` 类反馈，不改变摸头主交互的优先级。

#### Presence 定时器内

- 定时器继续作为“低频主动表达”的统一入口。
- 在现有 `deriveMoodState` 和 `maybeCreatePresencePulse` 之间或其附近接入 `playful presence` 判断。
- 由主流程统一决定是否 `notifyRenderer`，避免多处分散发状态。

## 数据流

### 聊天后

1. 用户发送聊天。
2. main 处理聊天成功结果。
3. 更新短期开心窗口。
4. 即时推送一次更偏开心的状态。
5. 后续 presence 轮询在窗口期内可低频触发轻量互动气泡。

### 摸头后

1. renderer 识别摸头并上报 main。
2. main 记录摸头事件和最近温度。
3. 更新短期黏人窗口。
4. 即时反馈继续沿用现有 `head-pat` / mood 推导。
5. 后续 presence 轮询在窗口期内可更容易产生亲近型轻气泡。

### 空闲时

1. presence 定时器触发。
2. 读取当前关系窗口、工作状态、阅读状态和时间段。
3. `playful presence` 判断是否应安静、是否应轻气泡、是否应收敛到夜间表达。
4. 若满足规则且不在冷却内，则推送一次低频表达。

## 规则建议

第一阶段不需要把所有阈值永久写死，但建议采用清晰、保守的默认值并集中定义：

- 聊天开心窗口：短时间有效，例如 `10` 到 `20` 分钟。
- 摸头黏人窗口：略长于聊天窗口，例如 `20` 到 `40` 分钟。
- 轻气泡冷却：至少按小时级控制，避免打扰。
- 夜间收敛：例如本地时间 `23:00` 到 `06:00`。
- 长时间工作阈值：继续沿用现有 `90` 分钟逻辑。

具体数值可在实现计划中落定，但必须遵循以下原则：

- 先保守，避免卡卡太吵。
- 所有阈值集中定义，方便后续微调。
- 优先保证“不会烦”，再追求“更活泼”。

## 错误处理与边界

- 如果关系记忆写入失败，不影响当前 UI 的即时状态反馈，只记录日志。
- 如果短期窗口字段缺失或旧数据没有这些字段，应安全退回到当前已有行为。
- 如果用户正在阅读、正在工作或刚触发过 presence 提示，优先静默。
- 如果未来资源包引入更多心情素材，本设计应允许扩展，但第一阶段不依赖这些素材。

## 测试计划

优先新增纯单元测试，覆盖以下规则：

1. 聊天后短时间内更容易保持活泼 / 开心。
2. 摸头后更容易表现亲近感。
3. 夜间会自动收敛，不频繁触发轻气泡。
4. `loading` / `thinking` 工作中保持静默。
5. 非工作空闲时允许低频轻气泡。
6. 冷却期内不会连续冒泡。
7. 缺少新字段的旧关系数据仍可安全运行。

如果实现中需要更新 `presenceService` 或 `chatMood` 的已有测试，也应保持测试重心在“规则纯度”和“回归安全”上，而不是只验证渲染细节。

## 成功标准

1. 卡卡在不增加新资源协议的情况下，看起来比现在更灵动。
2. 聊天后、摸头后、空闲时、夜间时，都有可感知但低打扰的差异化表现。
3. 工作状态下不会频繁打断用户。
4. 新逻辑集中在清晰的规则边界内，而不是散落在多个流程里。
5. 相关定向测试、全量 `npm test` 和 `npm run build` 最终都能通过。

## 后续演进

如果第一阶段效果稳定，下一阶段可以继续扩展为：

- 更完整的 mood 状态机与衰减机制。
- 基于关系阶段的更细分话术与主动表达。
- 更丰富的心情素材或 `variants`。
- 更明确的“撒娇 / 陪伴 / 安抚 / 困倦”节奏层。

但这些都不纳入本次 V1 范围。
